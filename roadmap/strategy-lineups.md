# Utility lineup library & replay aids — roadmap research

**Unit:** strategy-lineups · **Priority tier:** P3 · **Date:** 2026-11-10
**LoE (aggregate):** M — item 1 is a new library view + one storage home + a read-side clustering pass over events that are already stored (≈ up to a week); item 2 is mostly wiring existing radar/clipboard/PNG scaffolding to item 1's record (S).
**Feasibility:** high — throw/landing/bounce positions (float64), grenade type and thrower yaw are all already stored and the radar/camera scaffolding exists; blockers: pitch (the `setang` half) is stored nowhere today and needs an extract enrichment, a trajectory fit, or a user `getpos` paste, and "3D throw replay" must be scoped to radar per PRODUCT.md's 3D-replay non-goal.

## Items in scope

1. **Utility lineup library** — browsable lineups by map and type; user-created,
   shareable, and/or extracted by clustering similarly-thrown utility across
   or within matches — NOT bundled pro content
2. **Lineup replay aids** — 3D throw replay, screenshots and teleport command per
   lineup; `setpos`/`setang` clipboard export for practice

## Current state

- **Greenfield:** no "lineup" string exists anywhere in `src/` (grep), no table, no view. All capability below is assembled from existing pieces.
- **What a lineup needs vs. what the repo stores:**
  - **Thrower position:** the positions sidecar (`internal/sidecar`, 8 B/player/frame, 64 Hz) gives X/Y/Z + yaw at the throw tick — but quantized: `quantCoord` truncates to the 1.0 u grid (±1 u), `quantYaw` to 8 bits (1.406°/step, ±0.7°). Z is the pawn origin (`pl.Position()`); feet-vs-eye must be verified once against an in-game `getpos` sample before generating `setpos_exact`. The `grenade_throw` event's `pos_*` is full-float64 but is the **projectile spawn** (hand/eye offset), not the player origin.
  - **Yaw:** stored (sidecar byte; `engine.js` `lerpAt` interpolates it). Full-precision yaw at throw can be enriched (below).
  - **Pitch (aim height): NOT stored anywhere.** `extract.go` deliberately reads only `ViewDirectionX()` (yaw) into the positions stream — `ViewDirectionY()` (pitch) was dropped after it drew garbage view cones (CS2.md "Eye angles"); the state stream carries no angles either. Derivability candidates: **(a) extract-time enrichment** — the throw handler (`handlers.go` `events.GrenadeProjectileThrow`) holds `e.Projectile.Thrower` (`*common.Player`), so `ViewDirectionY()` + `Position()` are readable at the throw moment and could ride in the `grenade_throw` row's `detail_json` (no sidecar layout change, no new stream; old imports simply lack the key → unknown, fail-soft per pre-release policy) — cheap, unverified probe; **(b) UserCmd extraction** — CS2.md: demoinfocs decodes full user commands from public HLTV/GOTV demos (2.24M/1.72M rows, view angles match pawn eye angles 92–98 % within 5°) — that is the per-shot-aim-telemetry route, heavy; **(c) ballistic fit** from throw→bounce→det Z points — possible in principle but needs CS2 grenade physics constants (gravity, overhand/underhand launch speed, drag) looked up, not guessed; **(d) user-provided** — paste in-game `getpos` output (`setpos_exact …; setang_exact …`) when authoring. Verdict: aim height is *conditionally* derivable — flag (a) as the one to verify first; no route is confirmed today.
  - **Grenade type:** `events.weapon` + the canonical kind set `models.UtilityWeaponKind` (he/flash/smoke/molotov/decoy — Molotov ≡ Incendiary), frontend twin in `heatkinds.js`.
  - **Target/landing:** `grenade` det rows carry full-float64 `pos_*` (+ `detail_json.entity` join key), `grenade_land` for decoy rest, `grenade_bounce` rows for intermediates. Pairing precedent: `analytics.Utility` (nearest same-thrower/same-kind throw ≤30 s in-round) and the frontend's `renderer.js` `joinBounceVerts`/`flightSplits` (throw → bounces → det polyline, floor-aware per hop). **No per-frame projectile positions exist** (grenades are not in the positions stream — the export unit noted the same).
  - **Map:** `matches.map` column; pack ids in `frontend/public/maps/<map>/` (radar art + `transform` + `elevation_regions`). Lineup map keys must match pack ids or the preview has no radar.
- **Replay-aid precedents:** PNG snapshot already ships (`replay/input.js` `snapshot`, the `S` key → `download.js` `downloadCanvasPNG` → `save.js` native dialog); clipboard precedent `Replay.svelte` `copyText` (`navigator.clipboard.writeText`); throw deep-link already ships — Utility tab's "replay ▶" stamps `replayHash(matchId, filter, { tick, loop })` → `#/replay/:id?tick=&loop=` (±10 s loop via `entryLoopAround`); **radar without a demo exists**: `Heatmaps.svelte` loads a pack through `loadMapPack` + `makeTransform` with no engine — the template for a lineup preview canvas.
- **Storage precedents:** baseline `internal/store/schema.sql` applied on every Open (a **new table** is `CREATE TABLE IF NOT EXISTS` — zero migration; a new *column* on an existing table forces re-import, see the `attacker_inair` comment). User-data write precedents: `saved_filters`, `saved_queries`, `metrics`, `analysis_config` (store CRUD + service + generated bindings). SQL console catalog `internal/query/schema.go` `tableNotes` + the pinned readable-table lists in `query_store_test.go`/`query.go` must learn any new table. Data-dir user files precedent: `plugins/` + `internal/data` `EnsureDirs`. Share plumbing: `saveText`/`saveBlob` (native save) + `app.Dialog.OpenFile` (native open — the demo-import path) for import.
- **Per-map user-authored data is an OPEN cross-unit question:** `roadmap/replay-overlays.md` recommends the data-dir pack meta key (elevation_regions precedent + preserve allow-list) for callout zones and explicitly asks *this* unit to de-conflict the one home for user-authored per-map data; `roadmap/notes-drawings.md` settles only the per-match side and asks for one policy across both. Lineups are per-map but *not* install-derived (they must never be wiped by an asset re-extract), which separates them from the zones meta key.

## Implementation path

### 1. Utility lineup library — LoE: M

- **Record shape (described once, no version field — pre-release policy):** `map`, `kind` (utility kind), thrower origin `x,y,z` + `yaw` (+ `pitch` when known — absent = unknown, never guessed), `landing x,y,z`, optional stored trajectory verts (throw→bounces→det, so a lineup with no source demo still draws), optional `side`, `label`/`notes`, source `{matchId, tick}` for extracted / `null` for authored, created-at. Keyed `(map, kind)`.
- **Storage (recommendation):** one `lineups` table in the baseline `schema.sql` — precedent `saved_filters` (new table = no migration), SQL-console visibility = PRODUCT's data-portability floor, indexed browsing by map/kind. **Sharing = file export/import**, not sync: JSON through `saveText` (export) + `Dialog.OpenFile` (import), format documented once as THE current layout — the constitution's "no cloud" makes files the only share channel. Alternative under consideration: data-dir `lineups/<map>.json` (copy-a-file shareable, workspaces-friendly) — must be decided together with the zones unit's meta-key recommendation (see Dependencies); do not build twice.
- **Extraction = read-side clustering, NOT a new import-time analytics pass:** every input row already exists in `events`. New store read: `grenade_throw` + `grenade` (+ `grenade_bounce`) rows joined to `matches` for map (reuse `EventFilter.Kinds`/`BBox` for the scoped form; `idx_events_kind_match` covers the library-wide scan), pairing in Go exactly like `analytics.Utility` (or `detail_json.entity`). Then a **pure clustering pass**: same-lineup key = `(map, kind, throw-position bucket, landing bucket)` — bucket sizes are tunable constants that must be characterized per kind (smokes land tight, flashes/HE scatter) against the golden demo; emit **suggestions** (count = sample size, per the honest-metrics rule); the user accepts a suggestion → it becomes a stored row. Nothing is bundled, nothing is fetched — constitution-faithful built-ins (empty library ⇒ empty suggestions; the empty state must read as intentional).
- **Authoring (user-created half):** (a) **"Save as lineup"** from a replayed throw — Utility tab row or Replay at the throw tick: engine `lerpAt` gives thrower origin/yaw, the event rows give type/landing/verts, `matches.map` gives the map — the cheapest capture and the natural entry point; (b) **paste `getpos`** output for lineups practiced in-game (this is where a precise pitch arrives today); (c) later: click-to-place on the preview radar. Label/notes via `Dialog`/form fields.
- **Browsing UI:** a **new top-level view** (`#/lineups` prefix route — router `builder/sql/profiles` precedent — plus a sidebar nav entry and a CommandPalette action). Map picker: the Library map facet pattern (`cachedRead('ListMapNames')` unioned with distinct stored lineup maps, `SuggestInput`); type filter: the five utility kinds (`heatkinds`/`models.IsUtilityWeapon` vocabulary); list rows → detail pane (radar preview, path, teleport copy, PNG save, "watch in replay" deep link for sourced rows). `MatchPicker` is match-scoped and wrong for this surface; a match tab (Utility) is wrong too — the item is browsable *by map*, library-level.

### 2. Lineup replay aids — LoE: S

- **Scope ruling first:** "3D throw replay" is a competitor feature; PRODUCT.md lists **3D replay under Never** — interpret and deliver as **radar throw-path replay**; flag to the owner that no 3D reading is permissible.
- **Throw-path replay:** a static radar canvas for the lineup's map — `loadMapPack` + `makeTransform` with no engine (the `Heatmaps.svelte` precedent) — drawing the stored verts (or re-fetched event rows for sourced lineups) through the exported pure helpers `renderer.js` `joinBounceVerts` + `flightSplits` so multi-floor hops split by panel (Nuke). Small new component; no `renderer.js` surgery (avoids the merge-conflict surface every sibling unit warns about). If instead painted inside Replay, it becomes a world-layer pass — co-schedule with the overlays/video units.
- **Screenshot:** the existing PNG pipeline on that canvas — `downloadCanvasPNG` + `saveBlob` native dialog (replay's `S` snapshot already proves the pattern).
- **Teleport command (approved carve-out):** `copyText` precedent → clipboard text `setpos_exact x y z; setang_exact yaw <pitch>`. Yaw from the record; **pitch from the record's pitch field when present, else omitted with a UI note** (or completed via the user's `getpos` paste) — never a fabricated angle. Verify feet-vs-eye Z and the ±1 u / ±0.7° quantization against one in-game sample; extract enrichment (item 1 path a) removes the quantization for future imports only.
- **Full throw replay for free:** sourced lineups deep-link `replayHash(matchId, filter, { tick, loop: entryLoopAround })` — the bounce arc, sounds and context of the actual throw, existing today.

## Risks & unknowns

- **Pitch is the one real gap** (top risk): without it `setang_exact` is incomplete for every existing import. One golden-demo probe — read `Thrower.ViewDirectionY()` at the throw handler — decides whether route (a) works; trajectory fit (c) needs looked-up CS2 physics constants; UserCmd (b) is the metadata unit's turf. Until verified, the command ships yaw-only with an honest note.
- **Quantization vs. `setpos_exact`:** ±1 u truncation and ±0.7° yaw from the sidecar may or may not be acceptable in-game for practice — verify with one live sample; the extract enrichment (full float64 at throw) fixes future imports only (pre-release: no versioning, no re-import mandate — old demos just lack the field).
- **"Same lineup" bucket sizing is unproven:** type-dependent landing scatter (smoke tight, flash/HE loose) means the clustering constants need characterization against the golden demo and a tuning knob; clustering quality *is* the item's core unknown.
- **Multi-floor maps (Nuke):** throw and landing live on different floors; the record needs floor/z context or the preview must run `flightSplits` over pack panels — cheap but required for correctness.
- **Storage home is a cross-unit decision** (DB table vs data-dir meta key vs per-map file) — must be settled with the zones/annotations units before building, or it gets built twice.
- **Empty-library UX:** no bundled content is constitutional, so a fresh install shows zero lineups — the built-in must be the extraction flow over the user's own demos, presented as such.
