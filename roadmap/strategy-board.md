# Strategic board / tactic editor — roadmap research

**Unit:** strategy-board · **Priority tier:** P3 · **Date:** 2026-11-10
**LoE (aggregate):** L — this is a small editor sub-app, not a feature: a new top-level view with its own canvas (the replay renderer is engine-coupled and not reusable as-is), a drag-and-drop token layer, a phase/timing strip, a save/load + share surface, and a replay→board snapshot bridge — every piece frontend except one small storage service. The notes-drawings unit's M covers roughly the geometry/tool/persistence core *on an existing canvas*; the board adds a new surface + editor interactions + timeline + cross-view bridge, so full item ≈ 2× that. A stripped v1 (one map, drag tokens + drawn paths, single phase, save/load, no snapshot/timeline) would be M.
**Feasibility:** high — no blockers and no unverified data sources: radar, world↔image transform, player/grenade icon art, per-tick player transforms and grenade-throw world positions are all client-side today. Soft dependencies: the `lib/draw/` geometry module the notes-drawings unit is designing (must be shared, not forked — it does not exist yet), and one unsettled policy decision: the single home for user-authored per-map data (this unit, lineups, and callout zones all want it).

## Items in scope

1. **Strategic board / tactic editor** — drag-and-drop players and grenades, drawn paths, timings, save/load of tactics, snapshot import from a viewer frame; far down the road

## Current state

- **Greenfield.** No board/tactic/strategy code anywhere (`grep -i 'strategy|tactic|board'` over `src/` hits only unrelated words), and **no drag-and-drop anywhere in the frontend** (no `draggable`/`dataTransfer`/`dragstart` — the only pointer-drag precedent is the replay camera in `replay/input.js`). No per-map user-authored data of any kind exists yet (lineups and callout zones are roadmap-only; `schema.sql` has no tactic/lineup/zone table).
- **No map-only view exists.** Every radar surface today hangs off a match: Heatmaps is a `MATCH_TABS` entry, Replay is `#/replay/:id`. A board is a new top-level route (`#/board`-style prefix route) plus a `NAV_ACTIONS` sidebar/palette entry — the routing/nav wiring is mechanical (`lib/router.js` `parseHash`, `App.svelte` route switch, `nav.js`).
- **The static-canvas precedent is `HeatmapLayer.svelte`**, not the replay renderer: radar image + overlay on one `<canvas>`, all world↔image math through `mapxform.js` `makeTransform`/`loadMapPack` (the ONE pack reader), device-pixel backing, click→world mapping, no-pack fallback grid. `replay/renderer.js` (≈4.1k lines) is the draw-pipeline reference but is engine/tick-coupled — the board should be a light new canvas component modeled on HeatmapLayer, not a renderer fork.
- **Icons exist** for grenade tokens: `/api/icons/manifest.json` (IconService → `internal/mappack/icons.go`) serves extracted SVG silhouettes keyed by canonical equipment names ("Smoke Grenade", "HE Grenade", …) with a fail-soft text-label fallback (`lib/replay/icons.js`). Player tokens: `lib/replay/playercolor.js` (radar colors) + name/steamId from the sidecar `meta.players` slot table — but the renderer's `drawPlayers` dot style is not exported, so the board reimplements a simple dot/label (small).
- **Snapshot inputs exist per tick**: `engine.js` `frameForTick`/`lerpAt(slot, {x,y,z,yaw,alive})` + `state.tick` give player transforms at the current frame; grenade flights are reconstructible from `grenade_throw` event rows (world positions + projectile entity id in `detail_json` — the exact join `renderer.js` L494–543 documents). So "capture a viewer frame" is a pure frontend read — **no draw feed needed**; the board consumes replay *state*, and drawn paths come from the shared geometry module instead.
- **Timings have no precedent**: `RoundStrip.svelte` is round-level navigation and the replay transport is a clock — a phase/keyframe strip (per-phase token positions) is new UI, and its data model is the one genuinely open design question.
- **Persistence precedents split two ways**: SQLite user tables (`saved_filters`, `saved_queries`, `metrics`, `analysis_config` — service + generated-bindings CRUD) vs. data-dir JSON files (the per-match sidecars, which sit in an extract-owned dir whose reprocess `RemoveAll` is a known hazard — see notes-drawings). Tactics are per-map, not per-match, so they sidestep the match-dir hazard but must pick one of the two homes.

## Implementation path

1. **Shared geometry first (or in lockstep with notes-drawings).** The pure shape/serialization model (`lib/draw/`: world-space point arrays + style + anchor, plain-JSON shapes with **no format-version key** per pre-release policy) must be built surface-agnostic — board paths and replay drawings are the same model on different surfaces. Do not fork it if the notes-drawings unit hasn't landed yet; coordinate rather than duplicate (their note already names this unit as the second consumer).
2. **New view + route.** Prefix route in `router.js` (+ `router.test.js` pin), `NAV_ACTIONS` entry, `App.svelte` branch; view skeleton follows an existing simple view. CSS prefix unique to the component (e.g. `bd-`).
3. **Board canvas.** Radar base via `loadMapPack` + `makeTransform`, pan/zoom (a small camera — the HeatmapLayer/`screenToImage` style math, not the replay input stack), click→world. Tokens rendered on the canvas (players: color dot + label; grenades: extracted SVG icons via `iconURL`, text fallback), pointer-based drag (mode-gated so it doesn't fight pan — the same left-drag conflict notes-drawings flags, but here the board owns the interaction from day one).
4. **Tool palette + paths.** Popover/Dialog conventions for tool/color/width/clear; strokes through the shared geometry module, hit-test via its inverse. Undo/clear minimal; full select/move handles is the scope-creep trap (same advice as notes-drawings).
5. **Phase/timing strip.** Minimal honest model: a tactic = ordered phases; each phase stores token positions + path visibility (keyframes, not continuous animation — v1). A small strip component to switch/edit phases; interpolation/playback is explicitly out of scope for v1.
6. **Save/load.** Recommended home: **data-dir JSON files** (`tactics/<map>/<slug>.json` via a new path in `internal/data`), exposed through a small Go service over generated bindings (`ListTactics`/`GetTactics`/`SaveTactics`/`DeleteTactics`, cachedRead on the list) — shareable and human-readable (data-portability floor), survives reprocess, wiped by deep-clean by design. Export/import of a single tactic rides `lib/save.js` `saveText` + a native open-dialog read. **Co-decide this home with the lineups and callout-zone units first** (see Overlaps) — three units wanting per-map user data must not create three homes. No version key in the JSON.
7. **Snapshot import.** From Replay: a board-bound action serializing the current frame — `lerpAt` positions/alive/yaw per slot + `meta.players` identity + grenade flights active at `state.tick` — as a board starting position; hand-off via the durable route query (`router.js`/`nav.js` conventions, match id + tick), board reads and converts to tokens. Reverse hand-off (board tick → replay seek) is the same query pattern via `nav.replayHash`.
8. **Tests.** Geometry + snapshot serializer + phase model in `node --test`; palette/drag behavior in a `frontend/test/*.dom.mjs` jsdom harness; route parsing pin in `router.test.js`. No golden-fixture, extract, or schema implications.

- `lib/draw/` geometry module from **notes-drawings** (shared — flag: build it surface-agnostic); `replay/renderer.js` `chevronPath` conventions and paint-order documentation style as reference only.
- `lib/replay/icons.js` `iconURL`/`loadIconManifest` (grenade tokens, fail-soft), `lib/replay/playercolor.js` (token colors), sidecar `meta.players` (names/steamIds).
- `lib/replay/engine.js` `lerpAt`/`frameForTick` + `state.tick` and the `grenade_throw` event rows — the snapshot serializer's inputs.
- `lib/router.js` `buildHash`/`parseHash` + `nav.js` (route-query durable state, `replayHash`), `App.svelte`/`NAV_ACTIONS` view registration.
- `lib/components/Popover.svelte`/`Dialog.svelte` (tool palette, confirm), `lib/save.js`/`download.js` `downloadCanvasPNG` (board PNG export), `lib/services.js` `cachedRead`.
- Service/bindings pattern for the storage methods (precedents: `queryservice.go` saved queries, `analyticservice.go` saved filters); `internal/data` path helpers for the `tactics/` dir.

## Dependencies & overlaps

- **notes-drawings (P2) — shared geometry, hard-ish dependency:** the shape model/serialization/hit-testing must be one module used by both units; only the model transfers (board = static surface, no engine/tick anchors). If that unit stalls, the board can start on view/canvas/tokens/storage and leave paths last — but never duplicate the primitives.
- **strategy-lineups — same storage family:** per-map user-created, shareable content. Settle ONE per-map user-data policy (data-dir JSON vs DB table vs meta key) alongside this unit; the replay-overlays unit already demanded the same decision for callout zones ("agree on the owner of user-authored per-map world data"). Tactics are documents *referencing* a map, zones/lineups are geometry *on* a map — related but not identical; still one policy discussion.
- **Replay — snapshot source and bridge:** consumes engine state + grenade events (all existing); route-query hand-off both ways. No renderer changes needed.
- **Video/clips — burn-in contract is replay-only:** the board's own canvas exports PNG trivially (`downloadCanvasPNG`); "drawings burned in" concerns the replay canvas, so the board stays out of that contract. No coupling beyond shared `lib/draw/` serialization.
- **Annotations (per-match) vs board (per-map):** different persistence scopes — keep them separate homes by design (match sidecar vs data-dir tactics dir), don't merge.
- **Library/metadata/statistics:** `LibraryService.ListMapNames` feeds the map picker; no schema, job, or extract impact. **Localization:** new UI strings ride the future localization item. **CS2 domain:** none — no lookups needed (positions/tokens are app-side abstractions).

## Risks & unknowns

- **Editor scope creep is the classic trap** — handles, multi-select, copy/paste, undo stacks, animation playback. v1 must be pinned small (drag + draw + phases + save/load + snapshot); the timeline model especially can swallow weeks if allowed.
- **Storage-home policy is cross-unit and unsettled** — building tactics storage before the lineups/zones decision risks the exact fragmentation the consolidation conventions forbid. Decide first; the data-dir JSON recommendation above is a proposal, not a settled rule.
- **Dependency on an unbuilt module** (`lib/draw/`): notes-drawings is P2 and not started — the board either waits for the model or builds it surface-agnostic itself; a fork here is expensive to retrofit.
- **Product fit / nav noise:** P3 "far down the road" — a new sidebar entry for a niche power feature must not harm the cockpit-first default; owner may prefer gating it behind an existing surface (e.g. a map view or Replay) until it earns its rail slot.
- **Token roster semantics:** tactics are per-map, not per-match — v1 tokens are generic (5v5 colored tokens), not tied to a demo roster; snapshot import is the only roster-bound path. Ambiguity here (named players vs slots) is a small design decision, not a blocker.
- **No unknowns in CS2 data or backend risk** — the backend is a small CRUD service; everything hard is frontend interaction and model design.
